你新增一条“发出议程”，接着马上把它勾成已完成。界面上的两个动作都应该立刻生效。如果它们分别发出保存请求，而先发出的“未完成”最后才写进仓库，下次打开时勾就会消失。这次需要排的是保存的顺序。

切到本课的练习快照后，运行 `pnpm dev`，在终端给出的地址后加上 `/examples/todo-app/async.html`。页面从内存仓库读出任务。题目里你已经可以新增、勾选和改名，底部会显示“还有改动未保存”。点“重新打开应用”会重新读取同一个仓库，于是刚才的改动就看不到了。本节要补的是中间这段保存过程。

## 先读取，再开放编辑

`async-repository.ts` 给 Store 两个方法。`load(signal)` 返回整份列表，`save(snapshot, signal)` 确认发出时的那一份。这里的内存仓库每次读写要等 2.5 秒，下一节会把它换成 HTTP 仓库。

`createAsyncTodoStore` 用上一节的 `createAsyncResource` 读取任务。等列表装入模型后才进入 `ready`，这样用户不会在旧数据还没读到时就编辑一份空列表。首次读取失败可以重试，进入编辑状态后则由本地列表继续接收修改。入口里的“重新打开应用”会卸载旧 Store，并从同一个仓库创建一个新 Store。

同步和异步的 Todo 都用 `todo-model.ts` 分配编号、勾选任务和计算筛选结果。装入仓库数据用 `restoreTodos`，编辑用模型的命令。只有编辑才回调 Store 登记保存，所以加载成功时不会把刚读到的列表又写一遍。

## 一次只让一份快照在路上

把尚未确认的最新列表放进 `pending`。读取它，拿到本次要保存的 `snapshot`，再等 `repository.save` 完成。等待期间用户仍能继续编辑，新列表会替换 `pending`，已经发出的那份 `snapshot` 仍保持原样。

| 用户和仓库的动作                   | 正在保存的快照       | 当前待确认的快照 |
| ---------------------------------- | -------------------- | ---------------- |
| 新增“发出议程”                     | 新增，未完成         | 新增，未完成     |
| 勾选它，再把标题改为“发出下周议程” | 仍在保存新增时的列表 | 新标题，已完成   |
| 第一份确认                         | 开始保存最新列表     | 新标题，已完成   |
| 最新一份确认                       | 空闲                 | 无               |

确认后用 `pending() === snapshot` 判断还有没有新编辑。模型每次编辑都会创建新数组，数组引用在这里就代表一份快照。如果两者是同一份，可以清空 `pending`。否则继续循环，保存用户手头最新的整份列表。勾选后的中间版本已经包含在改名后的列表里，所以无需额外排一笔写入。

## 失败时把修改留在页面

保存失败时退出循环，保留 `pending` 和本地列表。点“重试保存”就会拿当前最新的列表再试。用 `AbortController` 占住正在写入的位置，它同时给卸载提供了取消句柄。如果仓库在卸载以后仍返回确认，已经关闭的 Store 也不能再发出下一笔写入。

`async-todo-store.test.ts` 里有一个用例专门挡住第一笔保存。它在这期间继续勾选和改名，先检查本地列表立即更新，再确认第二笔要等第一笔的 Promise 完成才会发出。
